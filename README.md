# Dispatcher 3.1

Google Apps Script для производственного диспетчера.

## Архитектура

- `Main.gs` — onEdit, FIFO-очередь событий и маршрутизация по этапам.
- `TableArchitecture.gs` — семантическая схема `field_key -> header -> current column` для листа `База`.
- `BaseRowLifecycle.gs` — безопасное очищение записей без физического удаления строк со spill-якорями.
- `Config.gs` — только стабильные координаты пользовательских листов A:L, ID внешних таблиц и Firestore-конфигурация. Фиксированных номеров столбцов `База` здесь больше нет.
- `Helper.gs` — UUID, checkbox-validation, семантические чтение/запись и формирование фактических строк.
- `Развертывание спецификации.gs` — Firestore и развёртывание спецификаций.
- `Удаление спецификации.gs` — сворачивание по нормализованному графу связей.
- Файлы этапов (`Склад.gs`, `Производство.gs` и т. д.) — специальная бизнес-логика соответствующего этапа.
- `Diagnostics.gs` — ручные тесты и диагностика.

## Семантическая схема таблицы

В Google Sheet существует скрытый лист `Схема`:

- `field_key` — стабильное техническое имя поля (`uuid`, `status`, `stage_stock`, ...);
- `header` — текущий человекочитаемый заголовок столбца `База`;
- `kind` — тип поля;
- `computed` — признак вычисляемого spill-поля.

Apps Script не обращается к `База` по буквам или фиксированным номерам столбцов. При первом обращении `TableArchitecture.gs` читает `Схема` и строку заголовков `База`, после чего строит карту фактических координат. Поэтому существующие столбцы `База` можно переставлять без изменения кода.

Если добавляется **новое поле, которое должно использоваться кодом**, оно добавляется одной строкой в `Схема`, после чего бизнес-логика обращается к его `field_key`.

`Настройки!B:B` хранит field_key этапов (`stage_design`, `stage_stock`, ...), а не буквы M, N, O и т. д.

## Вычисляемые столбцы

Вычисляемые поля `База` обслуживаются одной spill-формулой-якорем в строке 2. Apps Script не копирует и не создаёт формулы при добавлении новых строк.

Это устраняет formula drift: логика столбца существует в одном экземпляре, а не в сотнях независимых формул.

## Связи спецификации

Скрытый лист `Связи спецификации` нормализует человекочитаемое поле `Назначение` в отношения:

`child_uuid -> parent_uuid -> quantity`

Одна строка-компонент может иметь несколько родителей. Расчёт потребности и ABC-комплектующих использует этот граф вместо `SEARCH/REGEXMATCH` по всему текстовому столбцу.

Физическая смежность строк в `База` больше не является частью модели.

## Листы исполнителей

Пользовательский интерфейс A:L сохраняется стабильным. Данные A:J и специальные дополнительные поля формируются из единой скрытой проекции BA:BN, которая выбирает поля `База` по `field_key` через `Схема`.

Это заменяет набор независимых `QUERY(... select AA where Z=...)` и устраняет зависимость рабочих листов от физических букв столбцов `База`.

## Жизненный цикл строк

После перехода на spill-формулы рабочие операции не используют `deleteRow/deleteRows` для `База`, поскольку физическое удаление могло сдвинуть или удалить формулу-якорь строки 2. Завершённые/удаляемые записи очищают только фактические поля; вычисляемые столбцы остаются структурно неподвижны.

## Диагностика

Запустите `validateTableArchitecture()` вручную в Apps Script после структурных изменений. Проверка не изменяет данные и контролирует:

- наличие всех обязательных field_key;
- однозначность заголовков;
- наличие единственного spill-якоря вычисляемого столбца;
- корректность field_key в `Настройки`;
- наличие `Связи спецификации`.

Остальные ручные проверки также собраны в `Diagnostics.gs`; потенциально изменяющие данные функции помечены комментариями.
